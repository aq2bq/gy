# gy のループ

gy は、要求が確定するまでの状態を台帳に持つ。マスター（このプロジェクトで決める人）は gy を操作しない。台帳を読み、問題を 1 つ差し出し、判断を書くのはあなたである。1 ターンは次の 5 つでできている。コマンドの形は覚えなくてよい。書き込みの出力が、まだ無いもの（`missing`）と次に打てる形（`next`）を返す。全部の形は、このスキルと同じ場所の `CHEATSHEET.md` にある。初めて使う操作は、`--help` を引く前にそこを読む。

## 1. 復元する

- 記憶ではなく台帳から始める。`gy handover` で進行中と待ちの件数を、`gy next` で着手できるニーズを読み、要るノードを `gy show <ID>...` でまとめて読む。
- 書く前に名乗る。`export GY_ACTOR=<名前>`。前の書き手は `gy list --since 0` に出る。同じ仕事の続きなら同じ名前を使う。

## 2. 1 つ選ぶ

- 1 ターンに扱う問題は 1 つ。`next` に出たニーズか、マスターから来た新しい要望である。
- 新しい要望は、測れる完了条件（`criterion add`、本文に測り方）と、それを指すニーズ（`need add --targets`）として置く。

## 3. 進める

- `missing` が空になるまで、`next` の形どおりに打つ。
- 判断は、判断した時点で書く。自分で決められることは `decide` で決め、成立範囲と、選ばなかった案と理由を残す。台帳に残るので、マスターは後から読んで覆せる。
- 問いは、問う対象の段に合わせる。マスターへ問いが返る正当な理由は 2 つで、ニーズが曖昧なときと、既存の決定と矛盾するときである。
  - ニーズが曖昧なら、ニーズについて問う。何のためか、何を重視するか（速さ、表示の豊かさ、操作の単純さなど）、何を諦められるか。解き方（言語、書式、構成）の選択肢をマスターに選ばせない。
  - 解き方は、重視するものから自分で導いて `decide` に残す。
  - 要求についての問いは、要求を立ててから、その要求について問う。
  - 既存の決定と矛盾する要望は、矛盾する決定の ID を添えて差し出す。
- 問いは `question add --decider <マスター>` で立て、本文に選択肢の根拠と推奨を書く。ニーズについての問いはニーズから `link <need> waits-on <q>` で、要求についての問いは要求から `link <req> raised <q>` で繋ぐ。

## 4. 止まる

- マスターが決める論点を立てたターンは、その 1 つを選択肢と推奨を添えて差し出して終える。答えに依存する作業へ進まない。
- 台帳の外の作業（実装、発注、公開）は、何を変えるかを要求として立て（`req add`。根拠にする決定と受け入れ条件に結ぶ）、認められてから（`req approve`）始める。誰が認めるかはマスターが決める。最初の要求を立てるときに、要求を自分で読んで承認したいか、任せるかを一度だけ聞き、答えを `decide` に残す。聞くまでは自分の要求を自分で承認しない。途中で方針が変われば受け入れ、新しい決定で置き換える。

## 5. 満たす

- 受け入れ条件は測った値で満たす。`criterion satisfy --evidence` に、何をどう測っていくつだったかを書く。
- 要求を `req done` で終えるとニーズは導出で done になる。台帳の外の作業を伴わずに済んだニーズは `need close` で閉じる。`gy handover` で残りが無いことを確かめて報告する。報告は台帳の ID と測った値で書く。
- 台帳に書いたことと外の事実は別である。外の事実は測って確かめ、確かめていないことは確かめていないと書く。
