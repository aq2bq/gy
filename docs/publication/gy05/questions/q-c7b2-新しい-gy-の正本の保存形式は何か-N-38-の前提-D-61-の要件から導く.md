## 問い

N-38（正本を git の外に置き、ハッシュ ID、GY_ACTOR 必須の履歴、undo、ロックを持つ）の実装に先立ち、保存形式を決める。roadmap 未決 1。マスターは「良い案が思いついていない。要件次第」（opinions.md 58 行目）。lead が案を導き、マスターが確認する。

## 要件（D-61、D-77、AC-44〜46、AC-50、roadmap 1-5）

1. 1 コマンド 1 トランザクションの原子更新。途中で失敗したら何も書かれない
2. 競合検出。2 つのエージェントが同時に書いても正本が壊れない
3. 追記専用の履歴。いつ・誰が・なぜ・出典。本文と属性の書き換えも含む
4. undo
5. 移行で切れない履歴。正本は形式の版を持ち、古い版は写しを残して 1 トランザクションで移す
6. 正本は作業ツリーと git の外。台帳のための git も worktree も要らない
7. 中央の採番器を持たない（ID は接頭辞 + ハッシュ）
8. publish が「指定した時点と範囲」を再現できる

## 案

A. 追記専用の JSONL イベントログ + スナップショット（ファイル）。1 トランザクション = 1 行（複数ノードの変更をまとめた 1 イベント）を fsync 付きで追記。ロックは 0.4 と同じ fs2 の排他ロック。競合検出はログの末尾位置（開いた時の行数と commit 時の行数の比較）。履歴はログそのもの。undo は逆イベントの追記。移行は読み手の版を上げるだけでログは不変。publish は任意の行までの再生。スナップショットは読みを速くする派生物で、無くても再生できる。依存はゼロ。

B. SQLite（rusqlite bundled）。ACID と WAL による並行読み。履歴は events テーブル、undo は逆更新、競合検出は BEGIN IMMEDIATE + version 列。移行は schema migration で、履歴の表を保つ。C の依存とビルド時間が増え、人が中身を見るには sqlite3 が要る。

C. 0.4 と同じ YAML ファイル群 + ジャーナル。履歴はノードファイルに埋め込まれ、431 KB の 95% がスナップショットになった原因。要件 3〜5 を満たすには結局 A か B の仕組みが要る。

## 軸と評価

| 軸 | A JSONL ログ | B SQLite | C YAML 群 |
|---|---|---|---|
| 1 原子更新 | 1 行の追記 + fsync。行が途中で切れたら末尾を捨てて回復 | トランザクション | ジャーナルで回復（今と同じ） |
| 2 競合検出 | ロック + 末尾位置の比較 | BEGIN IMMEDIATE + version 列 | ロックのみ |
| 3〜4 履歴と undo | ログそのもの。逆イベント | 表。逆更新 | ノードに埋め込み（95% 問題） |
| 5 移行で切れない履歴 | ログ不変、読み手の版だけ上げる | schema migration | ファイル書き換え |
| 6 git の外 | どこにでも置ける 1〜2 ファイル | 1 ファイル | ディレクトリ |
| 7 採番 | 無関係 | 無関係 | 無関係 |
| 8 時点の再現 | 行までの再生 | 表の時刻で絞る | 不可 |
| 依存 | ゼロ | rusqlite（C、ビルド +数十秒） | serde_yaml |
| 実装量（600 行のニーズに収まるか） | 収まる見込み（0.4 の lock と journal の知見を再利用） | 収まるが SQL と型の二重定義 | 今のまま |
| 人が覗く | jq で読める | sqlite3 が要る | cat で読める |

## 推奨

A。理由は 3 つ。要件 3〜5 と 8 が「追記専用のログを再生する」という 1 つの仕組みで満たされる。依存を増やさない。移行で履歴が切れない（ログを書き換えない）ことを構造で保証できる。B に劣るのは並行読みの性能だが、利用者はエージェント 2〜3 で、Kokopelli の台帳は 213 ノード規模なので問題にならない。
