## 関係

## 成立範囲

CI の設定に適用する。開発の速さを優先し、他のプラットフォームは検証しないと文書に明記する。Windows の失敗はテストのパス区切りの前提（views/a.html が Windows では区切りが違う）によるもので、製品の欠陥ではなかった。性能の関門は、ブラウザ内の p95 が100ms未満と初期読込が10秒未満だけを残す。自動操作の往復はドライバと IPC と assertion を含み、ランナーの性能で変わる。GitHub の共有ランナーで3000ノードが638msとなり関門を超えたが、同じ実行でブラウザ内の p95 は通っていた。往復は測って証跡に残すが、関門にはしない

## 本文

## Context

クロコさんから、タグpushのCIで3000ノードの自動操作往復p95が638msとなり500ms関門に失敗したが、ブラウザ内100ms関門は通ったと報告された。リモート結果の報告者はクロコさんである。

## Decision

往復時間の測定と証跡を残し、500msの合否判定を削除する。初期読込10秒とブラウザ内p95の100msは維持する。

## Consequences

テスト全体の30秒制限が24回の自動操作往復を通じて同種の制限にならないよう、性能テストだけ120秒の停止検出枠にする。クラスタ開放の600ms特例も製品の応答時間基準ではないため、共通のassertion待機3秒へ統一する。正常系と欠陥注入で同じ検証を使用する。workers=1、retries=0は維持し、待機時間と製品の性能関門を区別する。その他の制限に今回観測された失敗はなく、無条件に引き上げない。
