## 本文

## 出所

gy の開発を gy で記録していた前任のクロコさんが 2026-09-13 に報告（Q-19）。`gy next` が実装と検収を終えた N-4〜N-7 を返し続けていた。

## 報告との差

報告は「`next` がニーズを除くのは `filed-as` の先の要求が完了しているときであり、Issue の無い gy 自身の開発には完了を記録する手段が無い」としていた。実装を読むと `need_done`（`crates/gy-core/src/views.rs:394`）の条件は2つある。

```rust
base_state(n.get("status")) == Some("complete")
    || (!n.refs("filed-as").is_empty() && ... すべて完了 ...)
```

第1の条件は need 自身の状態である。台帳の一時コピーで確かめた。

```
gy node set N-4 --set status=complete   → exit 0
gy lint                                  → no findings
gy next                                  → N-4 が消え、13件から12件になった
```

要求を経ずに完了を記録する手段は、0.3.1 に既に存在する。

## それでも問題である理由

手段があることを利用者が知る方法が無い。README の属性表は `status` を「11 requirement states, or `open` / `closed` for questions」と説明しており（README.md:128）、need に書けることが読み取れない。前任者が「記録する手段が無い」と結論したのは、文書がそう読めるからである。

さらに、誤った値は黙って無視される。`status: done` と書いても `base_state` は一致せず、need は完了と見なされないまま lint も何も言わない。記録したつもりが効いていない状態を検出できない。

根にあるのは、need のライフサイクルが設計として定義されていないことである。`need_done` という判定だけが実装に存在し、need がいつ完了するのか、誰が記録するのか、どの操作が何を判断するのかが `docs/architecture.md` に無い。AGENTS.md の「追加する属性や状態には、誰がいつ記録し、どの操作が何を判断するかを定義する」が、need の状態について満たされていない。

## 判定

Q-19 の選択肢はどちらも採らない。要求を経ない記録手段の追加（選択肢1）は不要で、過剰報告の受け入れ（選択肢2）は手段がある以上その前提が成り立たない。D-28 のとおり、既にある判定を設計として定義し、文書と検査をそれに一致させる。

need の完了に証跡を要求する専用の操作は足さない。`next` が実態を答えられれば目的は達する。証跡を伴う操作は「あると便利」に当たり、採用の理由にならない。
