# N-11 設計案 — Q-25、PO 判断待ち

gy の開発担当のデック先生です。実装には着手していません。適用対象は、設計担当が確定前に宣言したファイル範囲と、実装担当が報告した確定後のファイル一覧の照合です。

## 現行契約と提案共通の条件

`gy-core/src/workflow.rs` の `string_set` は文字列または文字列の組を完全一致で集合にします。`check_records` が equal / same-set / subset を実行し、現在の検査と保存履歴の検査から共用されています。既存の3種の意味、重複・順序の扱い、既存 profile の結果は維持します。

両案とも新しい比較種別を明示的に選択したときだけ適用します。以下の名称と構文は提案です。左辺は実装担当が記録した具体的な相対パスの配列、右辺は設計担当が承認対象の版へ記録した宣言の配列です。実装担当が任意の対応表を書いて検査を成立させる方式にはしません。

新比較では各宣言が具体的なファイル1件に対応し、各ファイルが宣言1件に対応することを要求します。未一致、1宣言に複数ファイルが一致、1ファイルに複数宣言が一致、重複宣言・重複報告をすべて拒否します。これにより「1 migration を宣言して2本を報告する」場合を落とせます。任意数の成果物を許可する機能は今回の提案に含めません。この重複の扱いも新比較だけの契約です。

比較はパス全体に対して大小文字を区別して行います。絶対パス、空のパス要素、`.` / `..` の要素、バックスラッシュを拒否し、パスの正規化で一致を補いません。gy は存在するファイル、実際の PR 差分、URL、採番日時を調べません。結果は報告同士の整合性です。

## 案 A: 設計側が glob を宣言する

新比較名の案は `matches-declared-globs`。設計の files は文字列配列のまま、例えば次を記録します。

```json
["src/retry.rs", "db/migrate/*_add_recurring_v2_enabled_to_tf_recurring_accounts.rb"]
```

実装側は具体的な文字列配列を報告します。文字列中の glob メタ文字は新比較の右辺でのみ解釈し、`*` は1要素内、`**` は複数のパス要素、`?` は1文字、文字クラスはその指定範囲に一致する契約とします。通常ファイルのメタ文字はエスケープが必要です。各宣言の照合数は共通条件どおり1件です。

設定担当は比較の kind を変えるだけで始められます。正確な桁数や文字種を指定するには glob の文字クラスを繰り返す必要があり、タイムスタンプ14桁などでは読みにくくなります。採用時には glob のエスケープ・文字クラス・エラー契約と依存ライブラリを確定する必要があります。

`**` により全ファイルに一致する宣言を書けます。1件制約で追加ファイルの混入は検出できますが、宣言1件に対する任意の別ファイルへの置換は検出できません。`db/migrate/*` も任意の migration 1本を許します。範囲の絞り込みを設計レビューへ多く残すため、コンテキストが厳しい局面で検査の価値が下がります。

## 案 B: 設計側が生成部分の文字種と長さを宣言する（推奨）

新比較名の案は `matches-declared-files`。設計の files を、完全一致か、生成部分を1箇所持つ宣言かのオブジェクト配列として定義します。

```json
[
  {"kind":"literal", "path":"src/retry.rs"},
  {
    "kind":"generated",
    "directory":"db/migrate",
    "prefix":"",
    "suffix":"_add_recurring_v2_enabled_to_tf_recurring_accounts.rb",
    "token_class":"ascii-digits",
    "token_length":14
  }
]
```

実装側は現行と同じ具体的なパスの文字列配列です。gy は generated 宣言の固定 directory、prefix、suffix を完全一致させ、その間の文字列を指定文字種・桁数で照合します。生成部分は最終ファイル名の1箇所に限り、パス区切りを含めません。directory は空文字（ルート）または固定の相対ディレクトリ、prefix/suffix は区切りを含まない固定文字列とします。prefix と suffix の少なくとも一方は非空、token_length は正整数です。文字種の初期候補は `ascii-digits` と `lowercase-hex` の2種です。

`**` や任意文字への一致を提供しないため、1宣言で全ファイルを許す形は書けません。一方、同じ固定部分と14桁の数字を持つ別ファイルは許可します。これは未確定部分を許すこと自体の限界です。日時の正しさや内容の同一性を確かめたとは扱いません。短い固定部分と長い可変部分の宣言は依然として広くなりますが、固定ディレクトリ・文字種・長さ・1件という境界を機械で維持できます。

設定担当は設計の files を object の variant として定義し直し、新比較を選びます。既存の FieldSchema の object / variants で宣言の形は表現できます。比較専用の必須条件と文字種・長さの検査は新比較の共通実装が担い、利用者に任意のチェックを組み立てさせません。設定量は A より増えます。生成ディレクトリ名、複数の可変部分、任意長の識別子はこの初期案では対象外です。必要な実例が出た時点で別途採否を判断できます。

## 採用時の実装・移行・互換性

| 対象 | 両案で維持・変更するもの |
| --- | --- |
| 既存比較・既存 profile | 変更なし。新比較へ自動変換しない |
| gy-core | 新比較の設定検査と記録間の照合を実装。CLI / MCP / lint / handover / 履歴で共用 |
| 派生表示 | 保存された宣言と診断を表示し、正本を書き戻さない |
| 過去の履歴 | 保存された旧 schema と旧比較で検査。新比較を遡及適用しない |
| 新規操作 | 採用後の profile を明示的に設定した記録で新比較を使用 |
| 既存の進行中記録 | 設計の宣言を書き換えるなら revision を上げ、対応する承認を記録する。新しい承認を過去にあったことにしない |
| 公開 API | 現行 CheckKind は公開 enum で non_exhaustive ではない。variant 追加は下流の網羅 match に非互換。版の判断は PO に依頼 |
| 保存形式 | 新比較を含む設定・履歴は旧バイナリで読めない。旧データを新バイナリで読む方向は維持 |

今回の新比較は、既存設計の表記訂正に対して過去の承認を引き継ぐ Q-23 を解決しません。既存記録への採用で設計データが変わる場合には、現行の revision と承認照合が働きます。今後の設計で未確定部分を先に承認対象へ含めれば、確定後のファイル名を理由に設計を書き直す必要がなくなります。

比較対象の取得は対象ノードの両記録に限定し、グラフや履歴全体の新たな走査を追加しません。A は各 glob を1回準備して照合し、B は固定部分と文字種を直接照合します。単純な実装は、宣言 D 件、報告 F 件、パス長 L に対し O(D×F×L)、対応件数の保持は O(D+F) です。現行検査が呼ぶノード・履歴の各比較でこの処理が発生します。採用後は小規模と大きなファイル一覧の実測でこの費用を確認します。

## 検証予定

AC-14 には、固定ファイルと生成ファイルの混在が通り、未宣言ファイル・別ディレクトリ・別 suffix・文字種違い・桁違い・2本への増加が落ちる例を置きます。欠落、重複、宣言の重なり、パスの非正規表記も境界として確認します。変更前の same-set / subset / equal の期待は維持し、旧履歴と新履歴を混在させます。拒否時の原子性、CLI と MCP の一致、lint / handover と遷移の診断一致を検証します。ここに書いた新比較のテストは未実装・未実行です。

PO への判断依頼: 案 B の制限付き生成宣言を採用するか、案 A の glob の汎用性を優先するか。B を推奨します。設定は増えますが、広すぎる宣言に対する境界を gy の型として定義できるためです。
